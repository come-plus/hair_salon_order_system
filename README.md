# Hair Salon Order System

美容室向け商品お取り寄せ・レビューカタログシステム

## プロジェクト概要

美容師が取り扱う商品（シャンプー、トリートメント、ミルクなど）のお取り寄せ依頼と、商品レビューの投稿・閲覧を、LINE公式アカウント経由で提供するシステムです。

顧客はLINE公式アカウントのリッチメニューから商品を選び、来店時に精算する仕組みを提供します（オンライン決済なし）。

## サイト構成のイメージ

### ① ブランド紹介ページ（`line_official_account_nissy` 側、既存）

各ブランドに2つの導線ボタンを設置。

- 「公式サイトへ」→ 外部サイトで直接購入（お客様自身で会員登録・購入）
- 「Nissyにお取り寄せ依頼」→ 本システムへ、該当ブランドが選択された状態で遷移

### ② 本カタログシステム（本リポジトリ）

**上部タブで探し方を切り替え:**

```
[ブランドで探す] [カテゴリで探す]
```

- **ブランドで探すタブ**: ブランド一覧 → 選択ブランドの商品一覧
- **カテゴリで探すタブ**: カテゴリ一覧（シャンプー、トリートメント等）→ 選択カテゴリの商品一覧（複数ブランド横断で表示）

商品データに「ブランド」と「カテゴリ」を両方持たせることで、同じ商品データを軸を変えて絞り込める設計とする。

①からの遷移時は、まず選択したブランドの商品一覧から開始し、そこから自由にタブ切り替え・カテゴリ横断で他の商品も閲覧できる。

## 主な機能

### 商品管理
- ブランド軸・カテゴリ軸、両方での絞り込み表示（タブ切り替え）
- 商品詳細ページ（画像、金額、説明文、レビュー）
- 商品一覧の管理画面

### お取り寄せ注文機能
- 複数商品の選択（チェックボックスまたはカート形式）
- 合計金額の表示
- 注文確定時の美容師への通知
- 決済機能: なし（来店時に施術費用と合算して精算）

### レビュー機能（フェーズ1.5で先行構築、本システムに統合予定）

商品ごとにレビューを閲覧・投稿できる機能。詳細仕様は`line_official_account_nissy`側のREADMEを参照。

- 上タブ「見る」「投稿する」
- 「見る」: レビューが存在する商品のみ表示。投稿画像（ビフォーアフター、最大4枚）。星評価なし
- 「投稿する」: 必須項目（商品名、使用年月日、お悩み、使ってどう変わったか）、任意項目（気に入ってる点、感想）、画像投稿（最大4枚）
- ルール: 同一商品・同一ユーザーは12ヶ月経過後に新規投稿可能。投稿は編集可能

### 外部サービス連携
- **LINE公式アカウント**: リッチメニューからのアクセス、注文通知
- **Square**: 予約管理、顧客情報、注文履歴の保持（検討中）

## 技術スタック

### インフラ構成

先輩のアドバイスにより、以下の役割分担で構成する。

```
Cloudflare（1アカウントで一元管理）
├─ ドメイン管理（全案件のドメインをここに集約。nissy-beauty.com含む）
└─ 静的ページ配信 + プロキシ（さくらへリクエストを転送）

さくらインターネット（1サーバー契約、アップグレード）
└─ ドメイン（案件）ごとにルートディレクトリを分離
     ├─ nissy-beauty.com 用フォルダ（PHP + MySQL）
     ├─ （将来の別案件）用フォルダ（PHP + MySQL）
     └─ （将来の別案件）用フォルダ（PHP + MySQL）
```

- サーバー自体は1契約で共有するが、ドメイン（案件）ごとにディレクトリを完全に分けるため、実質的にコードもデータも独立する
- MySQLもドメインごとに別々のデータベースを作成し、データが混ざらないようにする
- ドメインはCloudflareに一元化しつつ、動的処理・DBは案件ごとにさくら側で完全分離できるため、将来案件が増えてもリソースを他案件と共有しない

### アプリケーション技術スタック（フェーズ1.5〜2）

- **フレームワーク**: Laravel + React（Inertia.js）
- **データベース**: MySQL
- **ホスティング**: さくらインターネット

**選定理由:**
- 恵がすでに使い慣れている「さくら + PHP」の知見をそのまま活かせる
- Laravelは2026年時点でも総合力トップクラスと評価される安定した選択肢。認証・DB操作・ルーティングなどの基本機能が揃っており、開発速度と保守性のバランスが良い
- Inertia.jsを使うことで、SPA的なUI（React）とLaravelのルーティングを違和感なく組み合わせられる

## 使用方法

### 顧客側の操作フロー（お取り寄せ）
1. ブランド紹介ページで「Nissyにお取り寄せ依頼」をタップ
2. 本カタログシステムに遷移（該当ブランドの商品一覧から開始）
3. ブランド軸・カテゴリ軸を切り替えながら商品を探す
4. 商品を選択してカートに追加
5. 注文確認画面で合計金額を確認
6. 注文確定（美容師に通知が届く）
7. 来店時に商品受け取り＆精算

### 顧客側の操作フロー（レビュー）
1. レビュー専用サイト（またはカタログシステム内のレビュータブ）にアクセス
2. 「見る」でレビューのある商品を閲覧、または「投稿する」で新規投稿
3. 投稿時は必須項目・任意項目を入力し、画像（最大4枚）を添付

### 美容師側の操作フロー
1. 注文通知を受け取る
2. Squareで顧客情報と注文内容を確認
3. 商品を準備
4. 来店時に商品を渡し、施術費用と合算して決済

## API連携

### LINE Messaging API
- リッチメニュー設定
- 注文通知の送信

### ユーザーアカウント連携（検討中、2案）

**案1: LINEログイン**
- カタログサイト側に「LINEでログイン」ボタンを設置し、そこを起点にログイン・新規登録を行う
- 別途LINEログイン用のチャネルを新規作成する必要あり
- 自社サービス側を起点にしたログイン導線にしたい場合はこちら

**案2: Messaging APIのアカウント連携機能（現時点で有力）**
- LINE公式アカウントのトーク画面を起点に、Messaging APIの「アカウント連携」機能でユーザーIDを紐付ける
- LINEログイン用チャネルは不要（すでに利用中のMessaging APIのみで実現可能）
- なりすまし防止のnonce検証が組み込まれており、セキュアに連携できる
- 大まかな流れ:
  1. お客さんがリッチメニューから商品カタログへアクセス
  2. カタログサイト側で連携アクションを実行
  3. LINEプラットフォームが正当なユーザーか検証した上で連携完了
  4. 以降、注文時にLINEへ通知可能
- 参考: [LINE Developers - ユーザーアカウントの連携](https://developers.line.biz/ja/docs/messaging-api/linking-accounts/)
- リッチメニュー起点の導線と自然に噛み合うため、現時点ではこちらが有力

## 開発メモ

- 商品画像: メーカーから使用許可取得済み
- 決済機能: オンライン決済不要（来店時に現金/カード決済）
- フリーワード検索: 不要（ブランド・カテゴリ絞り込みのみ）
- ブランド紹介ページ（外部リンク集）と本カタログシステムは役割を分離: 前者は「外部で自分で買う」「Nissyに頼む」の分岐点、後者は「お取り寄せ注文専用の場所」
- レビュー機能は独立サイトとして先行構築せず、将来的に本システムに統合する方針（レビュー起点での購入導線を確保するため）
